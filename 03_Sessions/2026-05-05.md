# Session 2026-05-05

## Headline

Fixed access violation crash in the Seed Finder's worker processes.

## Problem

All spawned worker processes crashed with `OSError: exception: access violation reading 0x...` inside `find_seeds_batch` in `shuffle.dll`. The main process was unaffected; the crash reproduced on every worker on every search.

## Root Cause

`ctypes.byref()` is only valid as a *direct* foreign-function call argument. In `seed_search.py`, it was being passed to `shuffle_lib.find_seeds_batch` (a Python wrapper), which then forwarded it to the actual C call. This indirection caused the argument to arrive as a garbage pointer in spawned worker processes on Python 3.14.

## Changes (commit `3a11a8e`)

- **`seed_search.py`**: `ctypes.byref(out_count)` → `ctypes.pointer(out_count)` — creates a real `LP_c_int` with a strong reference, safe through intermediaries.
- **`shuffle_lib.py`**: Added `find_seeds_batch` smoke test inside `_load_c_shuffle()` so workers fail loudly at init (RuntimeError) instead of crashing mid-search with an access violation.
- **`compile_shuffle.py`**: Added `depth > num_levels` clamp in C to prevent reading past the `arr[]` stack buffer if a user manually enters an out-of-range depth. Fixed `→` arrow character (cp1252 encoding crash in error path).
- **`shuffle.dll`**: Recompiled from updated C source.

## Verified

Multiprocessing smoke test: single spawned worker, 8-level rush, seeds 0–5000 → worker exited code 0, found 121 seeds correctly.

## Session continuation (same date, separate plan: `resilient-sprouting-curry`)

### Headline

Fixed correctness bug + AV crash for seeds > 161,803,398: `SA[56]` was `long long`, should be `int` to match C# `System.Random` int32 wrapping.

### Root Cause

`long long SA[56]` in both `full_shuffle` and `find_seeds_batch` allowed values to escape `[0, MBIG-1]` during the warmup phase for seeds where `mj = 161803398 - seed < 0`. The unwrapped values eventually caused `j = -1`, writing to `arr[-1]`, corrupting the stack → AV. Additionally, any seed > 161,803,398 produced **wrong shuffles** silently, meaning prior seed search results for high seeds are suspect.

### Changes

- **`compile_shuffle.py` (`C_CODE`)**: `long long SA[56]` → `int SA[56]` in both functions; `SA[55] = (int)mj`, `SA[ix] = (int)mk`; warmup: `SA[i] = (int)((long long)SA[i] - SA[1+n])` (computes in 64-bit to avoid UB, truncates for C# int32 wrap); shuffle: `long long r = (long long)SA[ie] - (long long)SA[ixx]`, `SA[ie] = (int)r`.
- **`compile_shuffle.py` (`verify_dll`)**: Added high-seed cross-check section — DLL vs Python fallback for 6 seeds in [200M, INT_MAX]; crash-check call of `find_seeds_batch` over the previously-AV-ing range.
- **`shuffle_lib.py`**: Python fallback warmup: `SA[i] = ctypes.c_int(SA[i] - SA[1+n]).value`; `_C_SHUFFLE_CODE` updated to mirror new C source.
- **`shuffle.dll`**: Recompiled.

### Verified

- `compile_shuffle.py` → OK, including high-seed cross-check (6 seeds)
- `_seed_repro.py --probe` → A, C, D all pass; bisect finds no bad seed in [257,250,000, 257,500,000)
- `_seed_finder_test.py` → all 5 ground-truth pairs pass
